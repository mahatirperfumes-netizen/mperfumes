PERFUMERY POS & INVENTORY EXTENSION
Developer Requirements & Implementation Brief
For Mahatir Perfumes | Extend the existing POS; do not replace its core sales/accounting functions
1. Project objective
Upgrade the existing conventional POS into a perfumery-specific inventory, blending, production, bottling and sales system. The system must track purchased perfume oils, alcohol, additives, bottles, caps, sprayers, labels, boxes and other packaging from supplier receipt through formulation and production to finished perfume stock and final customer sale. Every stock movement must be traceable, costed and auditable.
Core rule: purchasing ingredients must not directly increase finished perfume stock; selling a finished bottle must not deduct raw materials again. Raw materials are consumed when a production batch is posted, finished goods are created from that batch, and sales deduct finished goods only.
2. Scope and design principles
Add a linked manufacturing / recipe module to the existing POS, retaining current checkout, customers, suppliers, payment methods, tax settings and sales reports wherever possible.
Use a perpetual inventory ledger: every receipt, transfer, adjustment, production issue, production output, sale, return and reversal creates a dated movement record.
Never silently overwrite posted transactions. Corrections must use a reversal/adjustment with a reason, user, timestamp and reference.
Support multiple units and controlled conversions (L, mL, kg, g, pieces). Do not assume 1 g = 1 mL for every ingredient. Store density where needed and preserve the original purchase unit.
Support multiple storage locations, at minimum: raw-material store, packaging store, production/WIP, finished-goods store and damaged/quarantine stock. Locations can be simplified if the business currently has one room.
Keep recipe versions, batch records, supplier lots and finished-batch traceability. The user should be able to identify which ingredient lots went into a finished product batch.
Build for small-business practicality: quick entry, barcode/SKU support, clear warnings, exports to Excel/CSV and an easy daily reconciliation.

4. Core workflow A — purchasing and receiving
Create a Purchase Order (optional but recommended) with supplier, expected items, quantity, unit, agreed cost, freight/other landed costs and expected date.
Receive goods against the order. Record actual received quantity, purchase unit, unit price, discount, freight allocation, supplier invoice number, invoice date, payment status and storage location.
Create a supplier lot/batch record for each received ingredient/component lot. If a supplier's lot number is absent, generate an internal lot ID and record it.
Only confirmed receipt increases available stock. A draft PO must not change inventory.
Allow partial deliveries, backorders, purchase returns, damaged/rejected quantities and supplier credit notes.
Calculate landed cost using a documented method (e.g., item cost plus allocated freight/fees). Store the method and allow a manager to correct it before posting.
Capture supplier payment/account payable in the existing accounting module if available; do not duplicate accounts payable in a disconnected module.
5. Core workflow B — formula / recipe management
Each sellable perfume should have a formula/Bill of Materials (BOM) with controlled versions. Example structure below is illustrative only; the developer must not hard-code these percentages.
Formula field
Requirement
Product / variant
Product name, size, target concentration, packaging configuration and formula version.
Ingredient lines
Ingredient SKU, target quantity or percentage, unit, permitted tolerance and optional preferred supplier/material lot rules.
Batch target
Target finished liquid volume or mass, number of bottles, and intended fill volume per bottle.
Calculation method
Allow formula by % w/w or % v/v, clearly marked per recipe. Do not mix bases silently. For mass-to-volume conversions, use an ingredient-specific density when required.
Packaging BOM
Bottle, cap, sprayer, label, carton and other components required per finished unit. Support optional packaging parts and different packaging variants.
Version control
Formula changes create a new version with effective date, author, reason and approval. Old batches remain linked to the version actually used.
Scaling
Scale ingredient quantities to batch size automatically; show target quantities and units before production is posted.
Confidentiality
Limit formula viewing/editing to authorized roles; record all edits.
Formula calculation rule: target ingredient quantity = formula proportion × target batch basis. If the formula is by weight, all formula proportions must be applied to the target mass; if by volume, to the target volume. Any density-based conversion must be explicit and visible.
6. Core workflow C — production / blending batch
Start a Production Batch from a selected product and approved formula version. Assign a unique batch number, such as MP-YYYYMMDD-001.
Enter planned batch size, planned number of bottles, production location, operator, date and notes.
Show ingredient availability by lot and location. Warn/block if there is insufficient available stock, expired/retest-due stock, quarantined stock or a unit-conversion problem.
Allow the operator to select the actual lot used for each ingredient and record actual quantity issued. Use FEFO (first-expiry-first-out) where expiry dates exist, otherwise FIFO, but allow authorized lot selection with a reason.
Record actual inputs, dilution/blending notes, mixing date, maturation start/end, filtering, transfer losses, samples taken and any rework. Do not force all stages into a complex workflow if the business chooses a simple process; stages should be configurable.
At the production posting step, deduct actual ingredient quantities from their raw-material lots and move the batch into WIP or completed liquid stock. Draft batches must not change inventory.
Record actual usable yield, waste/loss, QC status and production notes. Compare planned versus actual yield and flag variance above a configurable tolerance.
When bottling, consume packaging components according to actual quantities used, including damaged components, and record the number of bottles filled, rejected, samples and leftover bulk liquid.
Create finished goods only for units that have passed the required QC/release gate. Unreleased stock must not be available for sale unless a manager explicitly overrides with an audit reason.
Post the batch and lock its original record. Any correction uses a reversal or controlled adjustment, never a silent edit.
7. Core workflow D — bottling and finished stock
Support bulk liquid as a separate WIP/finished-bulk stock item, so a batch can be bottled in several sessions or sizes.
A bottling run links to the source liquid batch and records fill size, bottle count, actual fill losses, packaging usage and resulting finished-product lots.
Example: 1,000 mL available bulk can be bottled into 20 × 50 mL only if the recorded usable liquid supports it. The system must not create more saleable volume than available, allowing only an authorized documented tolerance.
If one formula is sold in 30 mL and 50 mL variants, each variant has its own sellable SKU and packaging BOM; both can consume the same bulk batch.
Finished stock must retain links to the production batch, formula version and ingredient lots for traceability.
8. Core workflow E — POS sale, return and exchange
At checkout, selling a finished perfume deducts the selected finished-goods SKU and, where lot tracking is enabled, the chosen finished lot. It must not deduct oils, alcohol or packaging a second time.
Block negative finished stock by default. If backorders/negative stock are permitted, make the policy explicit and restrict it to authorized users.
Sales returns must ask whether the returned unit is resellable, damaged, opened or quarantined. Only approved resellable units return to available stock; opened/damaged returns go to a separate non-saleable location.
Exchanges should be recorded as a return plus a new sale, preserving stock and financial audit trails.
Samples, testers, giveaways, staff use and marketing units must be recorded as separate stock issues with reason codes; do not disguise them as sales or unexplained stock adjustments.
Support discounts, customer orders, COD/paid status and existing POS payment flows without breaking current functionality.
9. Costing rules
Use a consistent costing method, preferably moving weighted-average cost for raw materials and finished goods unless the existing POS/accounting system requires FIFO. The developer must document the chosen method and apply it consistently.
Raw material cost consumed by a batch = actual quantity consumed × the applicable inventory cost per base unit, plus any directly attributable production costs configured by the business.
Finished batch cost includes consumed ingredients, packaging components used, and optionally direct labour/overhead. Clearly separate actual material cost from optional labour/overhead estimates.
Unit cost of finished goods = total batch cost allocated across good saleable units, with documented treatment for waste, samples, rejected units and remaining bulk. Do not allocate the full cost to saleable bottles while also retaining the same cost in remaining bulk.
Purchase freight/fees should be allocated consistently to landed costs. Avoid double-counting supplier invoice cost and landed-cost additions.
When costs change after a purchase, do not silently rewrite historical batch costs or sales margins; use the configured accounting policy and preserve transaction history.

12. Alerts and validations
Low stock and projected shortage based on recipes and open production plans.
Insufficient ingredient or packaging quantity before production/bottling.
Expired or retest-due material; quarantined/rejected lots cannot be issued without authorized override.
Unexpected yield, waste, fill-volume or stock variance beyond configurable tolerance.
Negative stock, duplicate supplier invoice number (where appropriate), duplicate barcode/SKU and missing unit conversion.
Finished product below minimum stock; optional suggested production quantity based on sales velocity.
Formula changed after a batch was started; require user to confirm which approved version applies.
13. Example end-to-end transaction (illustrative)
Purchase: receive 500 mL of a perfume oil, 5 L of alcohol and 100 bottles, recording supplier lots and landed costs. Production: create a batch using the approved formula; the system issues the actual recorded oil and alcohol quantities from those lots. Bottling: record the bulk quantity used to fill, for example, 10 × 50 mL bottles; consume 10 bottles, 10 caps/sprayers/labels/cartons as specified by the packaging BOM. Sale: sell 1 bottle at the POS; finished stock falls by one unit, while raw-material stock remains unchanged by the sale. Traceability: open the sold finished lot and see its production batch, formula version, and the source lots of oil/alcohol/packaging.
The quantities above illustrate the workflow only. The application must calculate quantities from the actual saved formula and actual recorded production results.

15. User interface requirements
Add clear menu areas: Inventory, Purchasing, Formulas, Production Batches, Bottling, Finished Goods, QC/Release, Stock Count and Reports.
Use searchable item pickers with SKU/name, unit, lot and available quantity visible. Show the base unit and conversion whenever an operator enters another unit.
Provide a printable production batch sheet and a bottling sheet for use at the workbench, with batch number, ingredients, actual quantities, operator initials and QC sign-off.
Provide fast mobile/tablet-friendly forms for receiving, weighing/measuring, bottling and stock counts.
Show status labels such as Draft, In Production, Maturing, Awaiting QC, Released, Partially Bottled, Completed, Cancelled and Reversed.
Allow Excel/CSV export and printable reports. Use local date/time and PKR currency formatting, configurable tax and current POS conventions.
16. Security, backups and reliability
Use database transactions so a production posting either completes all required inventory movements or none of them.
Prevent duplicate posting if a user double-clicks or the network retries a request.
Back up the database automatically and test restoration before launch.
Maintain an audit log and restrict destructive deletion of posted transactions.
Use role-based access, strong authentication appropriate to the existing POS, and protect supplier pricing and formula data.
If the POS is cloud-based or multiple terminals are used, handle concurrent stock deductions safely.

18. Acceptance tests — required before payment/sign-off
Receive a supplier delivery of oil, alcohol and bottles. Verify only received quantities increase and supplier lot/cost information is retained.
Create a formula and scale it to a target batch. Independently verify the displayed ingredient quantities and unit conversions.
Attempt production with insufficient oil. System must block posting or require a specifically authorized, audited exception; it must not create stock from nothing.
Post a production batch. Raw stock must decrease by actual quantities issued; the batch must retain ingredient lot and formula-version links.
Record waste and a lower-than-planned yield. The system must show the variance and allocate cost without creating excess finished stock.
Bottle two different sizes from one bulk batch. Verify bulk liquid and each packaging component decrease correctly and finished SKUs increase by actual good units.
Sell one finished bottle. Finished stock and COGS must decrease/increase correctly according to the costing policy; raw material must not be deducted again.
Return an opened bottle. It must not automatically return to sellable stock.
Open a finished lot and trace back to all ingredient lots and suppliers; open a supplier ingredient lot and trace forward to affected finished lots.
Reverse a posted transaction with a reason. Original and reversal must both remain visible and stock must reconcile.
Run a physical count and post an approved variance. Ledger, on-hand stock and reports must agree.
Verify cashier permissions cannot edit formulas, costs, posted production batches or stock adjustments without authorization.
19. Questions the developer must answer before coding
What technology/database does the current POS use, and can it support transaction-safe stock ledger entries and lot tracking?
How are existing products, purchase units, stock quantities, costs, sales and returns stored? What data migration is needed?
Will raw materials be measured mainly by mass (g/kg), volume (mL/L), or both? Which ingredients need density values?
Should costing use moving weighted average or FIFO, and how does this align with the current accounting records?
Will production include maturation/WIP stages, or should the first release use a simpler batch-to-bulk-to-bottle flow?
Which packaging parts are mandatory for each product/size, and which are optional (tester, gift box, sample, etc.)?
How will opening stock and opening costs be verified and signed off before go-live?
20. Definition of done
The extension is complete only when Mahatir Perfumes can trace a supplier purchase through ingredient lots, formula version, production batch, bottling run, finished product lot and POS sale; reconcile all stock movements; calculate finished-product costs using a documented policy; prevent accidental double deductions and unexplained negative stock; and export clear operational and profitability reports. A visually attractive interface without accurate ledger logic, traceability and acceptance-test evidence is not sufficient.
Appendix A — simple daily operating checklist
Receive and label every delivery before placing it into available stock.
Check the correct lot and unit before issuing ingredients to a batch.
Record actual quantities, not only planned quantities.
Record losses, samples, testers, damaged packaging and rework with reason codes.
Do not sell a finished lot before QC/release if the business uses a release gate.
Reconcile cash/POS sales and perform scheduled cycle counts.
Review low-stock, expiry/retest, batch variance and negative-stock alerts.
